# Live provider recovery qualification

Run this check against the deployed gateway and active controller before qualifying provider recovery. The ordinary test suite exercises code and simulated transports. Deployment acceptance requires a real signed capability round trip and measured stream continuity.

1. Submit a harmless provider operation through the normal signed site API while both Rover vision consumers are connected. Record the HTTP status, returned operation ID and lease ID under `submission` as `status`, `operation` and `lease`.
2. Read the result through the normal signed site API. Record each attempted result read under `results` with `status`, `operation`, `lease`, `state` and `has_result`. Confirm the exact lease reaches `released` and record its `operation`, `lease` and `state` under `lease_check`.
3. Observe the public and loopback Rover vision sockets from the Mac with `python -m tests.qualify_live_provider_recovery observe-streams --public <configured WSS vision URL> --bridge <loopback WS vision URL> --node-file <private node.json path> --window-seconds <seconds>`. Store its JSON under `streams` in the same evidence object. The observer records traffic counts and gaps without saving images or credentials.
4. Run `python -m tests.qualify_live_provider_recovery verify --window-seconds <seconds> --max-gap-seconds <continuity budget> --max-delivery-age-seconds <delivery budget> <evidence.json>`. The command exits nonzero on missing proof, any observed 429 or 503, an unreleased lease, a disconnected consumer, absent front or rear records, or a gap or delivery age beyond the specified budget. The gap includes silence before the first frame and after the last. Delivery age measures elapsed time from processing to receipt on the same Mac monotonic clock. Camera capture age requires a separately synchronized source clock.

Keep the result with the exact deployed image and rollout. Report the local test suite and the live qualification separately. Retain a failed qualification as an open production incident.

## Automated Mac production check

Run `python3 deploy/install-provider-qualification.py` on the Rover bridge Mac from the reviewed release. This installs a user LaunchAgent which reads the existing controller configuration and uses the installed Mac terminal OAuth transport to call the Site. Local GitHub job fixtures do not have these production credentials. The agent checks the active controller placement every five minutes. A changed placement starts a fresh check. For the same placement it rechecks an unsuccessful run after fifteen minutes and a successful run after an hour.

Each check opens both Rover sockets, submits one read-only `robot.vision.metadata:1` operation, reads its result through the normal Site API and looks up the exact lease by ID. It checks the operation, lease, task, terminal state and returned camera metadata. The observer decodes each distinct JPEG to pixels on each socket. A corrupt packet fails qualification and the same capture can still arrive intact on a retry. Source capture IDs distinguish new frames and telemetry from rewrapped records. Transport sequence changes and refreshed processing timestamps cannot advance an unchanged capture. Both sockets must meet the one-second continuity and delivery-age budgets across an 80-second window. Any observed API error fails the check.

The latest observation lives in `~/.local/share/biomerte-provider-qualification/latest.json`. It includes a success flag, sample timestamps, controller manifest and placement identity, per-socket measurements and the result of each attempted API call. Inspect the timestamp as well as the flag. `previous.json` retains the preceding observation. `last-measurement.json` preserves the most recent full round-trip and socket evidence through subsequent placement outages. Monitor reports contain no camera payloads or credentials. A qualification failure leaves the active controller and its leases available for investigation.

For an immediate retest after a repair, run `python -m tests.run_live_provider_recovery --force` from the reviewed checkout with the Mac vision environment's Python. The check uses one process lock across manual and scheduled runs. If a previous operation has an ambiguous outcome, the next run reconciles its original IDs. A separate fresh round trip is required for a pass. Restarting the monitor preserves those IDs.

Each newly observed active controller placement also gets one signed concurrency test. The monitor starts sixteen independently identified `core.echo:1` operations through the Site while both sockets are under observation. It reads an existing action and its released lease during the burst, then verifies the exact returned value and released lease for each of the sixteen operations. Both the initial and final observations must identify the same manifest, gateway epoch, worker, incarnation and grant. Changing one of these starts a new qualification. `--force` repeats the stream and metadata check and reuses the recorded pressure outcome for the same placement.

The `signed_pressure.receipt` path in `latest.json` points to `release-pressure/<placement hash>/first.json` under the qualification state directory. It preserves each initial response and timing. The monitor records each intended submission before sending it. After an interruption it reads already-started operation IDs and their leases without submitting again. `reconciled.json` records that later observation separately. A 429, 503, interrupted wave or mismatched result keeps the first pressure qualification failed even when all its actions later settle. For an independent manual observation run `python -m tests.qualify_signed_submission_concurrency` and retain its JSON separately.
